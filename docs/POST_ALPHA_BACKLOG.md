# 成章：Alpha 后需求池

> 文档状态：候选需求收集
> 更新日期：2026-08-07
> 当前版本范围：[ALPHA_REQUIREMENTS.md](./ALPHA_REQUIREMENTS.md)

## 1. 文档用途

本文件只收集 Alpha 完成后可能进入产品的需求。

这里的内容：

- 不属于 Alpha 范围；
- 不影响 Alpha 的验收和发布时间；
- 不代表已经承诺实现；
- 不预先指定技术方案；
- 需要根据真实文章的使用反馈重新排序。

候选需求真正进入开发前，应单独形成对应版本的需求文档和技术方案。

## 2. 排序原则

优先考虑：

1. 能直接减少从零散想法到文章完成的阻力；
2. 来自真实写作中的重复问题；
3. 能保护作者观点和个人语言；
4. 能减少用户必须承担的组织工作；
5. 相比新增功能，价值明显高于继续修复现有闭环。

不因为某项能力是成熟写作产品的常见功能，就默认提高优先级。

## 4. PA-01：轻量 inplace Markdown 编辑

### 用户问题

最终成稿和精修时，Markdown 语法标记可能增加视觉噪声，用户需要在编辑源码和阅读文章之间来回切换。

### 期望体验

- 直接在接近最终文章的视觉效果中阅读和修改；
- 标题、引用、列表和强调呈现为自然排版；
- 编辑当前位置时仍能看见并控制原始 Markdown；
- 可以随时切换到完整源码模式；
- 模式切换不会改变文章内容；
- 中文输入、选择文字、撤销和 AI 修改保持自然可靠。

### 边界

- Markdown 始终是文章的唯一内容格式；
- 不追求完整复制 Typora；
- 不因此扩展图片管理、可视化表格和富文本能力；
- 不能为了视觉效果牺牲内容完整性和编辑稳定性。

### 评估条件

完成第一篇真实文章后，判断 Markdown 源码是否已经成为显著阻力。如果主要问题仍是观点、结构或 AI 文字质量，则继续后置。

## 5. PA-02：捕捉后的 AI Idea 归属建议

### 用户问题

用户记录 Fragment 后，需要额外浏览和判断它属于哪个 Idea。随着 Fragment 和 Idea 增多，手动归属可能形成新的整理负担。

### 期望体验

- Fragment 保存后可以立即继续输入；
- AI 在后台给出少量可能相关的 Idea；
- 每条建议解释关联原因；
- 用户确认后才建立关系；
- 可以忽略或拒绝建议；
- 同一 Fragment 可以属于多个 Idea。

### 边界

- 建议不能阻断捕捉；
- AI 不能替用户静默归类；
- 不自动创建大量标签和 Idea；
- 不以整理准确率取代文章完成质量。

## 6. PA-03：跨 Idea 思想线索发现

### 用户问题

同一个长期观点可能在不同时间以不同形式出现，并散落在多个 Idea 中。用户难以发现它们之间的延续、冲突和变化。

### 期望体验

- 看见跨 Idea 反复出现的判断和问题；
- 看见同一观点随时间发生的变化；
- 发现值得发展为新文章的长期线索；
- 由用户决定是否合并、拆分或创建新 Idea。

### 边界

- 不展示复杂知识图谱；
- 不自动合并 Idea；
- 不把主题相似直接等同于思想线索；
- 建议必须可解释。

## 7. PA-04：更细粒度的内容来源说明

### 用户问题

随着 AI 参与组织和补写，用户可能难以判断文章中的关键表达来自原始 Fragment、自己的后续确认，还是 AI 新增内容。

### 期望体验

- 必要时能够查看段落依据了哪些 Fragment；
- 能区分用户原话、用户确认的推论和 AI 新增文字；
- 来源信息默认不干扰阅读和写作；
- AI 修改被接受后仍保留必要的来源关系。

### 边界

- 不建设复杂审阅系统；
- 不要求用户手动维护引用关系；
- 不因追踪来源而破坏正常编辑体验。

## 8. PA-05：作者偏好学习

### 用户问题

如果用户不断删除相同的 AI 句式、结构或语气，而系统每次仍然重复生成，AI 协作就无法真正变得个人化。

### 期望体验

- 系统逐渐减少用户经常拒绝的表达；
- 更愿意保留用户反复保留的原话和写作习惯；
- 用户可以查看、修正或关闭重要偏好；
- 可以选择历史文章作为风格参考；
- 个性化不能演变为机械模仿表面措辞。

### 边界

- 不编造用户立场；
- 不默认使用所有历史文章；
- 不把风格一致性放在观点准确性之前；
- 是否需要模型训练留到技术方案阶段决定。

## 9. PA-06：CMS 与博客发布集成

### 用户问题

文章生成 Markdown 后，用户仍需手动复制文件、填写元数据并发布。当文章完成量稳定后，这一步可能成为重复摩擦。

### 期望体验

- 在成章内维护最小发布信息；
- 将完成文章发送到一个真实博客目标；
- 明确展示发布成功、失败和重试状态；
- 保留 Markdown 导出作为始终可用的通用方式。

### 边界

- 首次只支持一个发布目标；
- 不同时建设多种博客适配器；
- 不扩展为完整博客主题和前台系统；
- 不在文章完成量稳定前建设内容日历、多渠道分发和 SEO 工具。

## 10. PA-07：移动端安装与离线能力

### 用户问题

Alpha 可以通过手机浏览器快速捕捉，但如果用户频繁受到启动路径、弱网或浏览器能力限制，移动 Web 可能仍不足以承接随时出现的想法。

### 期望体验

- 可以从手机桌面快速进入捕捉；
- 无网络时仍可放心记录，并在网络恢复后同步；
- 根据真实需要使用系统分享、快捷入口或通知等移动能力；
- 桌面与移动端看到一致的内容和保存状态。

### 边界

- 进入下一版本前再判断采用 PWA、原生 App，还是继续增强移动 Web；
- 不为了安装形态复制两套产品体验；
- 不在缺少真实使用证据时承诺完整离线能力；
- 无论选择何种形态，用户内容都应保持可导出和可迁移。

## 11. 维护方式

每完成一篇真实文章，使用以下问题更新需求池：

- 哪一步最阻碍文章继续生长？
- 哪个动作重复出现且适合由系统承担？
- 哪些 AI 判断反复错误？
- 哪些编辑动作最打断思路？
- 哪些候选需求并没有影响文章完成？

候选需求进入开发时：

1. 确认它解决了真实、重复的问题；
2. 将它移入新的版本需求文档；
3. 明确成功标准和不做范围；
4. 再形成对应技术方案；
5. 更新本需求池中的状态和目标版本。
