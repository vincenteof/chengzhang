# 成章：产品定义与 MVP 计划

> 状态：讨论稿  
> 更新日期：2026-08-05

## 1. 一句话定义

**成章，让闪现的想法自然长成文章。**

一个帮助创作者将持续积累的零散想法，逐渐发展为具有个人观点和个人声音的文章，并最终完成发布的辅助写作工具。

它不是一个「带 AI 索引的笔记软件」，也不是一个输入主题后自动生成文章的 AI 写手。它要解决的是从未完成的思想到可发布作品之间的转化问题。

## 2. 我们要解决的问题

### 2.1 用户现状

目标用户脑中经常出现有价值但不连续的表达。这些内容可能：

- 在不同时间、不同场景中产生；
- 围绕多个主题并行发展；
- 只有一句判断、一个比喻、一个例子或一段情绪；
- 暂时无法确定属于哪篇文章；
- 有个人辨识度，但尚未形成完整论点；
- 被记录下来后长期沉没，最终没有成为作品。

用户并不一定缺少想法，也不一定需要 AI 替自己写。他真正困难的是：

1. 及时保存稍纵即逝的表达，同时不被分类和整理打断；
2. 从长期积累的碎片中发现反复出现的思想线索；
3. 判断哪些想法值得发展成文章；
4. 找到文章真正独特的中心主张；
5. 组织论点、例子、经历、反例和叙事顺序；
6. 发现文章缺失的材料，并继续思考，而不是让 AI 用空话补齐；
7. 借助 AI 提高完成度，同时不失去作者的语言和思想所有权；
8. 将成稿顺畅地交付到个人博客。

### 2.2 现有工具的缺口

现有 AI 笔记工具主要解决「我以前记过什么」和「如何找到相关笔记」；AI 写作工具主要解决「如何扩写或润色当前文档」；CMS 主要解决「如何编辑和发布已经成形的文章」。

它们之间仍缺少一条连续链路：

```text
随手捕捉 -> 形成思想线索 -> 明确中心主张 -> 补足素材 -> 组织结构 -> 协作成文 -> 发布
```

本产品专注于这条链路，尤其是「思想线索到文章主张」这一段。

## 3. 目标用户

### 3.1 初始用户

- 有个人博客、Newsletter 或长期公开写作习惯的独立创作者；
- 经常产生想法，但难以组织和完成长文的人；
- 思维发散、并行、容易被复杂整理流程打断的人，包括部分 ADHD 用户；
- 重视个人表达，不接受批量生成式内容的人；
- 熟悉或愿意使用 Markdown 的创作者。

### 3.2 暂不服务的用户

- 追求按关键词批量生产 SEO 内容的团队；
- 需要多人审批、复杂权限和商业内容日历的编辑部；
- 主要需求是会议记录、任务管理或通用知识库的用户；
- 期望输入标题后直接得到可发布文章的用户。

ADHD 是重要的设计约束和种子用户特征，但不必成为产品唯一的市场标签。产品面向的是更广泛的「非线性思考、长期写作」场景。

## 4. 产品承诺

> 你只需要记下那些不想失去的念头。当它们足以成为一篇文章时，产品会帮助你看见它。

产品不是替用户凭空制造观点，而是帮助用户：

- 保存原始思想；
- 发现跨时间的联系；
- 看见观点中的张力；
- 明确真正想表达的主张；
- 判断还缺少什么；
- 将已有思想组织成作品。

## 5. 产品原则

### 5.1 捕捉时零组织

记录时不要求选择文件夹、文章、标签或内容类型。分类发生在捕捉之后，且 AI 建议不能打断输入。

### 5.2 AI 先理解，后写作

AI 的默认职责依次是连接、提炼、追问和组织。只有用户明确授权后，AI 才能补写或润色正文。

### 5.3 不消除有价值的矛盾

相互冲突的碎片不应被自动合并成平滑的总结。矛盾可能正是文章最独特的思想张力，应该被展示给作者判断。

### 5.4 区分作者内容和 AI 内容

原始碎片必须永久保留。AI 新增的观点、推论和文字应可识别、可撤销，并能追溯其依据。

### 5.5 底层网络化，界面单焦点

同一碎片可以关联多条思想线索，但界面一次只强调一个当前任务，避免给发散型用户增加认知负担。

### 5.6 完成作品，而不是维护系统

产品价值以文章是否开始、完成和发布衡量，而不是笔记数量、标签完整度或知识图谱规模。

## 6. 核心概念模型

### 6.1 Fragment：碎片

用户捕捉的最小原始单位，可以是一句话、一段文字、一个问题、例子或引用。

核心属性：

- 原始内容；
- 创建时间；
- 来源和上下文；
- 是否为用户原话；
- 关联的 Thread；
- 是否已被文章采用。

MVP 先支持纯文本，语音、图片、链接解析后置。

### 6.2 Thread：思想线索

围绕某个未完成问题或判断持续生长的碎片集合。它不是文件夹，也不等同于主题标签。

例如，「AI 写作」是主题；「真正个人化的 AI 写作应学习删改，而不是模仿措辞」是一条思想线索。

Thread 可以由用户创建，也可以由 AI 建议，但归属和拆分必须由用户确认。同一个 Fragment 可以属于多个 Thread。

### 6.3 Claim：候选主张

AI 基于 Thread 中已有素材提出的文章中心判断。一个 Thread 可以同时保留多个候选主张，用户可以选择、修改或拒绝。

候选主张不是摘要。摘要描述「这些内容谈了什么」，主张回答「作者究竟想让读者相信什么」。

### 6.4 Question：待回答问题

AI 发现的观点缺口、事实缺口、矛盾或需要补充的个人经历。问题的目标是帮助用户继续思考，而不是诱导用户接受 AI 的结论。

### 6.5 Draft：文章草稿

围绕已确认 Claim 组织的 Markdown 文档。草稿包含文章结构、正文和段落来源关系。

### 6.6 Source Link：来源关系

记录草稿段落使用了哪些 Fragment，以及其中哪些文字由 AI 新增。这是保持作者所有权和建立信任的关键能力。

### 6.7 Publication：发布记录

保存标题、slug、摘要、标签、发布时间、发布目标和状态。MVP 仅保留最小字段，为后续 CMS 能力预留模型。

## 7. 核心用户流程

### 阶段一：捕捉

1. 用户进入产品后立即看到输入区域；
2. 输入一段零散想法并提交；
3. 系统保存原文，不要求用户分类；
4. 后台分析可能的关联，但不打断下一次输入。

### 阶段二：发现思想线索

1. 系统定期或在用户主动请求时分析未处理碎片；
2. 展示可能属于同一思想线索的碎片组合；
3. 解释建议关联的原因，而不只给出标签；
4. 用户确认、拒绝、拆分或合并 Thread；
5. 系统保留用户决策，后续减少重复错误。

### 阶段三：形成主张

1. 用户打开一条 Thread；
2. 系统展示原始碎片、内部关系和明显矛盾；
3. AI 提出 2 至 3 个不同方向的候选主张；
4. 用户选择、修改或自行写出主张；
5. 系统识别主张当前具备的素材和缺口。

### 阶段四：继续生长

1. 系统提出少量、高价值的追问；
2. 用户的回答作为新 Fragment 保存，而不是直接吞入 AI 总结；
3. 新素材继续影响 Thread、Claim 和缺口判断；
4. 用户决定何时进入成稿，不由系统强制推进。

### 阶段五：组织文章

1. AI 根据同一 Claim 给出 2 至 3 种结构方案；
2. 每种方案说明叙事方式、适用素材和仍缺失的内容；
3. 用户选择结构并调整章节；
4. 系统把 Fragment 放入对应章节，形成带来源的文章骨架。

### 阶段六：协作写作

用户可以对选中内容执行不同权限的 AI 操作：

- `组织`：只调整已有文字和顺序，不新增观点；
- `追问`：针对缺口提出问题；
- `补写`：生成过渡或段落，明确标记 AI 新增内容；
- `润色`：改善表达，保留指定原话；
- `反馈`：指出论证、节奏、重复和不清晰之处，不直接改写。

所有操作均以建议或可撤销变更呈现。

### 阶段七：交付与发布

1. 用户完成 Markdown 草稿；
2. 填写最小发布元数据；
3. 预览文章；
4. MVP 导出 Markdown，或推送到一个预先选定的博客目标；
5. 后续版本扩展定时发布、版本管理和多渠道分发。

## 8. MVP 定义

### 8.1 MVP 要验证的核心假设

> 当用户积累了 10 至 30 条杂乱碎片时，系统能否帮助他发现一个真正属于自己的中心主张，并在不稀释个人表达的情况下完成一篇文章？

MVP 的重点不是证明 AI 能生成文章，而是证明以下过程成立：

```text
碎片积累 -> Thread 得到确认 -> Claim 得到认可 -> 缺口得到补充 -> 文章得到完成
```

### 8.2 MVP 必做范围

#### 账户与存储

- 单用户使用；
- 本地开发环境可运行；
- 持久化保存 Fragment、Thread、Claim、Question 和 Draft；
- 基础自动保存和数据导出。

#### 碎片捕捉

- 无分类要求的文本快速输入；
- 碎片时间线；
- 编辑、删除和恢复；
- 将碎片手动加入或移出 Thread。

#### Thread 工作区

- 创建、重命名、合并和拆分 Thread；
- AI 建议关联碎片，并说明关联原因；
- 用户确认或拒绝建议；
- 展示一条 Thread 中的原始素材。

#### 主张与追问

- 基于选定碎片生成多个候选 Claim；
- 用户选择、修改或拒绝 Claim；
- 识别矛盾、重复和素材缺口；
- 生成少量追问；
- 将回答保存为新的 Fragment。

#### 结构与写作

- 基于已确认 Claim 生成多个文章结构；
- 将碎片分配到章节；
- Markdown 编辑与预览；
- `组织`、`补写`、`润色`、`反馈`四类明确的 AI 操作；
- 段落与原始 Fragment 的最小来源追踪；
- AI 新增内容的视觉标识及接受/拒绝。

#### 交付

- 标题、摘要、slug 和标签；
- 导出标准 Markdown；
- 保留文章与原始素材的关系；
- 至少实现一个完整示例从捕捉走到导出。

### 8.3 MVP 暂不实现

- 完整博客前台和主题系统；
- 多用户、团队协作和权限；
- SEO 评分和内容营销建议；
- 定时发布和多渠道分发；
- 语音、图片、网页剪藏和 PDF；
- 自动创建大量标签或知识图谱；
- 移动原生应用；
- 自训练模型或模型微调；
- 全自动模仿个人文风；
- 根据标题一键生成整篇文章；
- 复杂版本控制和审阅流程。

### 8.4 可选的最小发布集成

只有在 Markdown 导出闭环稳定后，才选择一个发布目标进行集成：

- Git 仓库中的 Markdown 内容目录；或
- Ghost Admin API；或
- 用户现有博客提供的 Webhook/API。

MVP 只选择一个，不同时建设多种适配器。

## 9. 页面与信息架构

MVP 预计包含五个主要界面：

1. **Capture / Inbox**：快速输入和最近碎片；
2. **Threads**：活跃思想线索及待确认的 AI 建议；
3. **Thread Workspace**：碎片、候选主张、矛盾和追问；
4. **Draft Editor**：文章结构、Markdown 正文、来源和 AI 操作；
5. **Library**：草稿、已完成文章和导出状态。

默认首页应服务于「立即记录」和「继续一个正在生长的想法」，而不是展示文件树或统计仪表盘。

## 10. AI 行为边界

每次 AI 操作都应接收明确的模式和约束，不能依赖一个通用聊天框承担所有任务。

### 10.1 允许的默认行为

- 引用用户原始内容作为判断依据；
- 发现相似、因果、对立、例证等关系；
- 提出多个候选解释；
- 明确说明不确定性；
- 指出缺口并追问；
- 在用户指定范围内重组文本。

### 10.2 禁止的默认行为

- 编造用户经历、立场、数据或引用；
- 把所有矛盾强行归纳为单一结论；
- 未经授权直接覆盖原文；
- 用通用正确但空泛的内容填补素材不足；
- 把 AI 推断伪装成用户原话；
- 捕捉完成后立刻弹出大段分析打断用户。

### 10.3 风格学习方向

MVP 不训练专属模型，只记录以下信号，为后续个性化提供基础：

- 用户保留和拒绝了哪些 AI 建议；
- AI 草稿与用户最终版本的差异；
- 用户标记为必须保留的原话；
- 经常被删除的词语、句式和结构；
- 已发布文章作为可选择的风格参考集。

## 11. 成功指标

### 11.1 核心结果指标

- 从至少 10 条碎片成功形成一篇用户认可的文章；
- 用户认可最终 Claim「确实是我想表达的，而不是 AI 替我发明的」；
- 用户认为最终文章仍然具有自己的声音；
- 原本停留在碎片阶段的想法最终完成并导出或发布。

### 11.2 过程指标

- Thread 关联建议的确认率；
- 候选 Claim 的选择或修改率；
- 追问带来的新增有效 Fragment 数；
- 最终文章引用原始 Fragment 的比例；
- AI 补写内容的接受、修改和拒绝比例；
- 从创建第一个 Fragment 到开始 Draft 的时间；
- 从开始 Draft 到完成文章的时间。

### 11.3 迭代方式

不设置独立的前期人工验证阶段。先快速实现一个可运行的最小闭环，从第一个版本开始使用真实想法写真实文章，并在使用中迭代。

- 每次迭代都保持「捕捉 -> Thread -> Claim -> Draft -> Markdown 导出」可用；
- 开发者本人是第一位持续用户，所有核心功能优先接受真实写作检验；
- 每完成一篇文章，记录阻塞写作的步骤、错误的 AI 判断和被大量修改的生成内容；
- 优先修复妨碍文章继续生长的问题，不按功能数量衡量进度；
- 不等待功能完整才开始使用，也不为了收集指标增加早期产品复杂度；
- 产品决策以真实文章的完成质量和作者感受为主要依据。

## 12. MVP 开发阶段与任务拆分

实施采用纵向切片。第一阶段就交付最薄但完整的创作闭环，之后每个阶段都保持产品可用，不先建设大量底层能力再等待集成。

### Phase 0：可运行的最小纵向闭环

目标：尽快得到一个能够真正写出文章的版本。

- [ ] 确定 Web 技术栈、数据库和首个模型提供商；
- [ ] 建立最小 Fragment、Thread、Claim 和 Draft 数据模型；
- [ ] 实现一个快速文本捕捉入口和碎片列表；
- [ ] 支持手动选择多个 Fragment 组成 Thread；
- [ ] 调用 AI 生成 2 至 3 个候选 Claim；
- [ ] 选择 Claim 后生成一个可编辑的文章结构；
- [ ] 提供基础 Markdown 编辑和预览；
- [ ] 导出标准 Markdown 文件；
- [ ] 增加必要的持久化、错误提示和最小测试；
- [ ] 使用产品完成第一篇真实文章。

这一阶段不做自动聚类、复杂来源追踪、发布集成和风格学习。界面可以粗糙，但不能用一次性脚本代替真实交互。

验收标准：应用可本地启动，用户可以把一组真实碎片变成 Claim 和 Markdown 草稿，并成功导出文章。

### Phase 1：让捕捉和 Thread 真正可日常使用

目标：降低长期积累碎片和整理并行想法的摩擦。

- [ ] 优化快速捕捉、自动保存和键盘操作；
- [ ] 实现碎片时间线、编辑、删除和恢复；
- [ ] 实现 Thread 创建、重命名、合并和拆分；
- [ ] 实现 Fragment 与 Thread 的多对多关联；
- [ ] 实现 AI 关联建议并说明理由；
- [ ] 实现建议的确认和拒绝；
- [ ] 在首页展示最近活跃的 Thread；
- [ ] 使用真实日常输入修正错误关联和界面负担。

验收标准：产品可以连续日常使用，用户无需预先分类即可捕捉内容，并能从真实碎片中维护多条并行 Thread。

### Phase 2：帮助思想继续生长

目标：让产品从整理素材升级为发现和发展文章主张。

- [ ] 实现完整 Thread 工作区；
- [ ] 展示碎片之间的相似、因果、对立和例证关系；
- [ ] 实现多个候选 Claim 的生成、选择和编辑；
- [ ] 识别矛盾、重复、论据和素材缺口；
- [ ] 生成少量高价值追问；
- [ ] 将用户回答作为新 Fragment 回流；
- [ ] 由用户确认何时进入成稿阶段；
- [ ] 用实际写作结果持续调整提示词和结构化输出。

验收标准：用户能从一组零散素材中确认一个属于自己的中心主张，并通过追问补充文章真正需要的内容。

### Phase 3：保护作者声音的协作写作

目标：提高文章完成度，同时避免生产作者自己都不理解的 AI 文字。

- [ ] 生成多种文章结构并说明差异；
- [ ] 实现结构调整和 Fragment 到章节的分配；
- [ ] 完善 Markdown 编辑、预览和自动保存；
- [ ] 分别实现组织、补写、润色和反馈操作；
- [ ] 实现 AI 变更的接受、拒绝和撤销；
- [ ] 实现段落到 Fragment 的来源追踪；
- [ ] 明确标记无原始素材支撑的 AI 新增内容；
- [ ] 记录 AI 内容在最终文章中的保留和修改情况。

验收标准：用户能理解并确认文章中的关键判断，最终草稿可以区分作者原始内容、作者确认的推论和 AI 补充文字。

### Phase 4：发布闭环

目标：让完成的文章直接进入个人博客流程。

- [ ] 实现标题、摘要、slug 和标签编辑；
- [ ] 完善桌面和移动文章预览；
- [ ] 保持标准 Markdown 导出稳定；
- [ ] 选择并实现一个最小发布适配器；
- [ ] 记录草稿、完成和发布状态；
- [ ] 使用产品持续完成并发布真实文章。

验收标准：至少一篇真实文章从闪现的想法开始，在产品内完成并发布到真实博客。

### Phase 5：边用边迭代

以下方向不预先排定固定顺序，根据真实使用中出现频率最高、最影响文章完成的问题决定：

- [ ] 基于编辑差异建立个人风格偏好；
- [ ] 增加语音和移动端快速捕捉；
- [ ] 支持更多博客发布目标；
- [ ] 增加定时发布和发布历史；
- [ ] 支持跨 Thread 的长期思想演化；
- [ ] 改进来源追踪和作者理解检查；
- [ ] 评估多人协作和编辑反馈；
- [ ] 评估本地优先、端到端加密或 BYO Model。

## 13. 风险与待验证问题

### 13.1 AI 过早收敛

风险：AI 很快给出一个听起来完整但平庸的总结，导致用户停止继续思考。

验证：比较「先给主张」与「先展示关系和矛盾」两种流程对最终文章独特性的影响。

### 13.2 自动关联不可信

风险：错误聚类会让用户觉得系统不理解自己，并增加整理成本。

验证：所有关联先作为建议，记录确认率，并测试同一 Fragment 属于多个 Thread 的情况。

### 13.3 AI 语言覆盖作者语言

风险：文章更加流畅，但失去个人辨识度。

验证：追踪原始 Fragment 使用率、AI 内容拒绝率和最终编辑差异。

### 13.4 流程过重

风险：Thread、Claim、Question 等概念虽然合理，但可能让用户觉得自己在管理项目，而不是写作。

验证：对象模型可以存在于底层，界面只在当前阶段暴露必要概念；观察用户是否能在没有教程的情况下推进。

### 13.5 发布功能分散重点

风险：过早建设完整 CMS，消耗大量时间，却没有验证核心写作价值。

验证：先使用 Markdown 导出和单一适配器，只有出现稳定完成量后才扩展发布管理。

## 14. 当前产品边界

长期愿景是「从想法捕捉到个人博客发布」的一体化创作环境；MVP 则是一个更窄的创作者辅助写作工具。

当前最重要的边界是：

```text
不是帮助用户管理更多笔记，
而是帮助用户完成更多真正属于自己的文章。
```

在核心假设得到验证之前，任何不能直接改善「发现主张、补足思想、组织成文」的功能都应谨慎进入 MVP。
